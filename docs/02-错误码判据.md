## 二、逐个码的实测证据

### 2.1 `250013` = 请求没被认 → 冷启动刷新

**关键实验（2026-10-27）**：

| 场景 | 同样的请求 | 返回 |
|---|---|---|
| 页面已存活数小时（当天 08:00 / 10:00 两场） | `{award_id, address_id, address_snapshot_id}` | **全是 `250013`** |
| `am force-stop` + 重载活动页之后 | **一字不差的同一个请求** | **立刻变成 `300001`** |

**旁证**：连打 5 发（间隔 900ms），5 发全是 `300001`、零 `250013`。
说明冷启动之后请求**持续**被认，不是偶然一次。

**推论**：`250013` 不是「时间没到」，而是「**服务端不把这次请求当成有效参与**」。
页面/会话状态（某个 token、session、页面初始化状态）决定了这一点。

**对策**：`grabber.run(cold_start=True)`（默认就是 True），
或设备端 guard 的 `am force-stop` + deeplink 冷启动。

> ⚠️ 冷启动会**清掉页面里的 sniper**，所以顺序必须是
> **先冷启动 → 再连接 → 再武装**。代码里已经是这个顺序。

### 2.2 `250017` = 限流 → 改串行链

**实验（窗口关闭时打请求，本该全是 250013）**：

| 5 发 / 间隔 | `250017`（限流） | `250013`（正常） |
|---|---|---|
| **0ms**（并发齐射） | **4** | 1 |
| 200ms | 3 | 2 |
| 400ms | 2 | 3 |
| **800ms** | **0** | 5 |

→ 结论：**并发/快速连发会被限流**。

**但更关键的第二个实验**：

| 打法 | 实测速率 | 限流 |
|---|---|---|
| 一次并发发 N 个 XHR | — | **被限流** |
| 间隔 900ms 串行 | 1.1 发/秒 | 无 |
| **「收到上一发响应再发下一发」串行链** | **11.6~12.2 发/秒** | **零限流** |

实测数据（串行链 12 发）：

```
#0  at=0ms    rtt=84ms  ec=300001
#1  at=84ms   rtt=90ms  ec=300001
#2  at=174ms  rtt=90ms  ec=300001
...
#11 at=984ms  rtt=89ms  ec=300001
```

**12 发只用 0.98 秒 → 12.2 发/秒，一个 250017 都没有。**

**原理**：限流看的是「**并发在途请求数**」或「到达速率」。
串行链每发都等响应（RTT ~90ms），在途永远只有 1 个，
所以不被限流 —— 而速率自然就是 `1 / RTT ≈ 11 发/秒`。

**对策**：`sniper.js` 用串行链：

```js
x.onload = function () {
  ...记录结果...
  fire();        // ← 收到响应立刻发下一发，不做 setTimeout 间隔
};
```

参数：`gapMs=0`、`attempts=120`（约 10 秒覆盖）。

> 旧版 `sniper.js` 是「40 发 / 15ms 间隔」的并发密齐射 ——
> 从第 2 发起全是限流垃圾，`state` 看着正常（`attempts=50`）实际**从没真正参赛**。
> 这是 10-09 之后一直抢不到的直接原因之一。

### 2.3 `300001` = 真进窗口，只是没抢到

**实盘（2026-10-27 20:00 场）**：冷启动 + 900ms 间隔，40 发
**全部 `300001`**、零 `250013`、零 `250017`。余额未扣。

**含义**：服务端认为**这次请求在窗口内、参与了竞争**，但没抢到（慢了一步/没货）。

**注意**：`300001` 在场次进行期间**一直会返回**（哪怕库存早没了）。
2026-10-27 19:15（10:00 场已开 9 小时）打请求也是 `300001`。
所以**不能用它来判断「窗口是否打开」**，只能看 `ec=0` 判断成功。

**对策**：提高密度。从 1.1 发/秒提到 11.6 发/秒后，当晚 22:00 场就抢到了。

### 2.4 `0` = 成功

**实盘（2026-10-27 22:00 场，第 16 发命中）**：

```json
{"success":true,"error_code":1000000,"result":{"success":true,"error_code":0}}
```

命中位置 `drift=+975ms`、`rtt=462ms`。
余额 **131 → 3**（扣 128），该场 15 件商品里**只有目标变成 `status=11`（已兑换）**。

**成功判据（三重确认）**：

1. 响应 `result.success === true` 且 `result.error_code === 0`
2. 商品 `status` 变 `11`
3. 余额减少对应卡数

## 三、怎么快速定位（排查流程）

```
1. python -m pddgrab.cli probe --item 汰渍
   ├ 报错 → 链路问题（frida/选页/页面不可见），先修链路
   └ 通过 → 目标可抢，继续

2. 打一发试试（fire 小规模）
   ├ 250013 → 冷启动没生效，检查 cold_start / guard 的 force-stop
   ├ 250017 → 还在用并发打法，检查 gap_ms 是否为 0
   ├ 300002 → 对时/时间不对，检查 _stm offset 与场次 start_time
   └ 300001 → 真竞争，密度不够 → 提高 attempts / 确认串行链速率

3. 看速率对不对
   串行链应该是 ~11 发/秒（RTT ~90ms）。
   如果只有 1 发/秒 → 还在用 setTimeout(gapMs) 而不是串行链。
```

## 四、附：券是「链路试金石」

券（`PERCENT_COUPON_EXCHANGE`，**1 张卡一张**）是**不限时间、随时可兑**的。
用它来验证「请求链路是否通」：

```bash
python -m pddgrab.cli coupon --yes     # ⚠️ 会真的花掉 1 张卡
```

* 券兑成功（`ec=0`）→ 说明**接口、签名、参数、地址全都没问题**，
  实物抢不到就是窗口/资格/密度问题。
* 券也失败 → 说明是请求本身的问题（参数缺、签名没带上等）。

2026-10-27 就是用这一招**证明「代码没问题」**的：同一套请求兑券成功、兑实物失败，
所以差异只在实物的时间窗口与资格。
