# 03 · 开火策略：三个要素

一次能抢到的开火，靠三件事同时成立。缺一个就是「没抢到」，但失败表现不同。

| 要素 | 作用 | 失败表现 | 参数 |
|---|---|---|---|
| **① 冷启动刷新会话** | 让请求被服务端「认」 | `250013` | `cold_start=True`（默认） |
| **② 串行链（密度）** | 每秒能打多少发 | `250017`（并发）或 `300001`（太慢） | `gap_ms=0`、`attempts=120` |
| **③ 首发提前到 T-1s** | 兜住库存释放点 | `300002` 或全 `300001` | `from_ms=-1000` |

---

## 一、① 冷启动刷新会话

**为什么**：页面/会话存活久了，兑换请求会被判 `250013`（请求没被认）。
`am force-stop` + 重新加载活动页之后，**同样的请求立刻变 `300001`**。
详见 [02-错误码判据 §2.1](02-错误码判据.md#21-250013--请求没被认--冷启动刷新)。

**怎么做**：

```python
device.cold_start_pdd()     # force-stop → sleep 3 → deeplink → sleep 14
```

**顺序不能错**：冷启动会杀掉页面里的 sniper，所以必须
**先冷启动 → 再 frida 连接 → 再武装**。
`grabber.run()` 已经按这个顺序编排。

**设备端等价物**：`guard.sh` 在唤醒后第一件事就是 `am force-stop` + deeplink。

---

## 二、② 串行链：把密度从 1.1 提到 11.6 发/秒

### 并发 vs 串行（实测）

| 打法 | 实现 | 速率 | 限流 |
|---|---|---|---|
| 并发齐射 | 循环里一口气发 N 个 XHR | 高但无效 | **被限流 `250017`** |
| 定时串行 | `setTimeout(fire, gapMs)` | `1000/gapMs` 发/秒 | 无（但慢） |
| **响应串行链** | `x.onload` 里直接 `fire()` | **`1/RTT` ≈ 11.6 发/秒** | **零限流** |

### 关键代码（`sniper.js`）

```js
function fire() {
  var x = new XMLHttpRequest();
  x.open('POST', XCHG, true);
  x.onload = function () {
    // 记录这一发的结果（drift / ec）
    shots.push(...);
    if (应该继续) fire();        // ★ 收到响应立刻发下一发 —— 串行链
  };
  x.send(body);
}
```

没有 `setTimeout`、没有间隔、在途永远只有 1 个请求。
速率由 RTT 决定（实测 ~90ms → 11 发/秒）。

### 为什么「在途只有 1 个」就不被限流

限流看的是**并发在途请求数**或**到达速率**。串行链每发都等响应，
在途恒为 1，所以既不触发并发限流，速率又天然很高。

> 这也解释了为什么旧版「40 发 / 15ms 间隔」反而更差：
> 它一次性制造了 40 个在途请求 → 触发限流 → 从第 2 发起全是 `250017`。
> `state` 显示 `attempts=50` 看着很努力，实际一发都没参赛。

## 三、③ 首发提前到 T-1s：库存是 T+900ms 才放的

**实盘证据（2026-10-27 22:00 场，命中那场）**：

```
#0  drift= -1000ms  ec=300001
#1  drift=  -996ms  ec=300001
#2  drift=  -890ms  ec=300001
#3  drift=  -793ms  ec=300001
#4  drift=  -426ms  ec=300001
#5  drift=  -343ms  ec=300001
#6  drift=  -266ms  ec=300001
#7  drift=  -178ms  ec=300001
#8  drift=  -101ms  ec=300001
#9  drift=   -26ms  ec=300001
#10 drift=   +62ms  ec=300001
#11 drift=  +138ms  ec=300001
#12 drift=  +642ms  ec=300001
#13 drift=  +727ms  ec=300001
#14 drift=  +812ms  ec=300001
#15 drift=  +889ms  ec=300001
#16 drift=  +975ms  ec=0        ★★★ 命中
```

**读法**：从 T-1s 到 T+889ms 一直是「在窗口内但没抢到」，
**T+975ms 那一发才命中** —— 说明**库存在 T+900ms 左右才释放**。

**推论**：
* 只从 T0 开始发 → 前面几发全打在「库存还没放」的空档，可能刚好错过释放点。
* 从 T-1s 开始连续发 → 释放点必然被某一发兜住。
* 10-09 那次「第 44 发才命中」也是同一个道理。

**参数**：`from_ms = -1000`（首发相对场次开始的偏移，负数 = 提前）。

## 四、演进数据（2026-10-27 一整天）

| 场次 | 打法 | 速率 | 错误码 | 结果 | 结论 |
|---|---|---|---|---|---|
| 08:00 | 900ms 间隔，页面存活很久 | 1.1/s | **全 `250013`** | 没抢到 | **请求没被认** |
| 10:00 | 同上（换商品也没用） | 1.1/s | **全 `250013`** | 没抢到 | 换商品解决不了资格问题 |
| 20:00 | **冷启动** + 900ms 间隔 | 1.1/s | **全 `300001`** | 没抢到 | 资格修好了，**密度不够** |
| **22:00** | 冷启动 + **串行链 gap=0** | **11.6/s** | 300001 → **第 16 发 `ec=0`** | **✅ 抢到** | 三要素齐了 |

**注意 20:00 → 22:00 的差别**：只改了一个参数（`gap_ms: 900 → 0`）。
同一份代码、同一个商品类别，结果从「没抢到」变「抢到」。

## 五、调参速查

```python
from pddgrab import grabber

grabber.run(
    item="汰渍",          # 或 award_id=1402434
    cold_start=True,      # ★ ① 必须 True
    gap_ms=0,             # ★ ② 0 = 串行链（不要设成 1~799 的并发区间）
    attempts=120,         # ② 覆盖约 10 秒
    from_ms=-1000,        # ★ ③ 提前 1 秒
)
```

命令行等价：

```bash
python -m pddgrab.cli fire --item 汰渍 --attempts 120 --gap 0 --from-ms -1000
```

**什么时候要调**：

| 现象 | 调什么 |
|---|---|
| 全是 `250013` | 确认 `cold_start` 生效（看日志里有没有「冷启动」） |
| 出现 `250017` | `gap_ms` 必须是 0；确认用的是串行链不是并发 |
| 全是 `300001` 且量很多 | 密度已到位，是纯库存竞争 → 考虑换便宜商品或多账号 |
| 出现 `300002` | 时间不对，检查 `_stm` offset 和场次 `start_time` |
