# 04 · 底层机制（改注入/选页代码前必读）

这一篇记的是「为什么代码要写成这样」—— 每一条都是踩出来的。

---

## 一、拼多多用的不是系统 WebView

`dumpsys activity top` 里的视图树：

```
com.xunmeng.pinduoduo.widget.nested.OverFlingWebView
mecox.webkit.WebView
mecox.provider.impl.InternalWebViewImpl
```

**`mecox` 是拼多多自带的 WebView 实现**，位于
`/data/user/0/com.xunmeng.pinduoduo/app_meco_64/dexs/dex_*/SystemWebViewApk`。
它**不继承** `android.webkit.WebView`，所以：

* `Java.use("android.webkit.WebView")` → 找不到实例（`Java.choose` 返回 0）
* 挂在 `android.webkit.WebView.loadUrl` 上的钩子**永远不触发**

---

## 二、mecox 在另一个 classloader 里

`Java.use("mecox.webkit.WebView")` 直接 `ClassNotFoundException`。
必须遍历 classloader 找到能解析它的那个，再用它建 ClassFactory：

```js
var mecoLoader = null;
Java.enumerateClassLoadersSync().forEach(function (ld) {
  if (mecoLoader) return;
  try { ld.loadClass("mecox.webkit.WebView"); mecoLoader = ld; } catch (e) {}
});
var cf = Java.ClassFactory.get(mecoLoader);
cf.choose("mecox.webkit.WebView", { onMatch: ..., onComplete: ... });
```

---

## 三、每次 `Java.registerClass` 会把拼多多搞崩

第一版捕获脚本每调一次 `evaluateJavascript` 就注册一个匿名 `ValueCallback` 类，
几十次之后拼多多 **SIGSEGV**（栈在 `frida-agent-64.so`），进程重启。

**修法：整个脚本只注册一个回调类**，用 FIFO 队列把结果分发给对应的 Promise。

```js
var CbCls = null;
function cbClass() {
  if (CbCls) return CbCls;
  CbCls = Java.registerClass({
    name: "pddxValueCallback",
    implements: [Java.use("android.webkit.ValueCallback")],
    methods: { onReceiveValue: function (v) {
      var r = pending.shift(); if (r) r(String(v));
    } }
  });
  return CbCls;
}
```

`getUrl()` / `evaluateJavascript()` 都必须在 **UI 线程**上调（`Java.scheduleOnMainThread`）。

## 四、`frida.attach()` 要 int pid，不是字符串

`dev.get_process("com.xunmeng.pinduoduo")` 会 `ProcessNotFoundError` ——
`frida-ps` 里拼多多的进程名是**应用标签「拼多多」**。

而且 `frida.attach()` 的 pid 参数**必须是 int**；
传一个长得像数字的字符串，frida 会把它当**进程名**去找，
报 `unable to find process with name '24395'`。

```python
dev.attach(int(pidof_output))     # ✅
dev.attach("24395")               # ❌ 被当进程名
```

## 五、★ 为什么必须在页面里发请求（不用逆签名）

`promotion-*.js` 里的 axios 请求拦截器：

```js
R = function (e) { return { name: "appendAntiContent", request: function (t) {
  if (!1 === t.needAntiContent && !t.useNativeAntiToken) return t;
  var n = getCurrentPlatform(), r = n.isNativePlatform, o = n.version;
  return t.useNativeAntiToken && r && compareVersion(o, "4.69.0") >= 0
    ? t                                   // ← 原生 App ≥4.69：JS 什么都不加
    : d.getAntiContent(e.serverTime).then(function (e) { ...anti_content... });
}}};
```

也就是说：**在 8.26.0 这种原生 App 里，`anti_content` 不是 JS 生成的，是原生网络层注入的。**

**推论（实测成立）**：只要请求是从这个 WebView 的 JS 里发出的，原生层就会给它签名。
所以我们不需要逆 `libpdd_secure.so`、不需要复现签名算法 ——
在页面里发一个普通 `XMLHttpRequest` 就行。

> 这也解释了「为什么不能 curl」：脱离 WebView 就没有那层原生签名，请求会被判非法。
> 想脱离 WebView，就得去逆 native 签名，那是另一个量级的工程。

**落地代码**：`panel._xhr()` —— 拼一个在页面里执行的 JS 片段，
发 XHR、把结果写到 `window.__pddr`，PC 侧轮询读回来。

## 六、★ 选页：必须按活动 id 精确匹配，并排除心跳页

拼多多**同时开多个** `attendance.html` WebView（实测）：

| index（**会变**） | URL | 内容 |
|---|---|---|
| — | `sjs_blank_heart_beat.html` | 心跳页，空 |
| — | `attendance.html?**id=197270**` | 标题「首页搜索ddd可以找到本活动」，只有整点抢券时间条 |
| — | `attendance.html?**id=195846**` | 标题「**减减卡兑好礼**」，**实物兑换列表在这里** |

**三个坑**：

1. **只按 `"attendance"` 匹配会选错页** —— 选到 197270 那个。
2. **选错页的后果很隐蔽**：那个页在后台，`visibilityState=hidden`，
   而**后台 WebView 的事件循环被冻结** —— `evaluateJavascript` 同步返回值正常，
   但 **XHR 回调永远不触发**。表现是 sniper 装上去、`state` 看着正常，
   却永远卡在 `syncing`（日志里是 `stm timeout`）。
3. **心跳页会报 `visibilityState="visible"`**，但异步回调同样不触发 ——
   所以「按 visible 选」也会被它骗。

**加固后的选页逻辑**（`webview.Bridge.resolve_target`）：

```
1. URL 同时含 "attendance" 和 "195846"，且不含 heart_beat/sjs_blank
2. 退一步：URL 含 "attendance"，且不含心跳特征
3. 再退：m.pinduoduo.net 的页面，且不含心跳特征
4. 都没有 → 抛错（**绝不退到心跳页**，那等于装了个死 sniper）
5. 在候选里优先选 visibilityState 含 "visible" 的
```

另外：**WebView 的 index 顺序会来回变**（195846 见过是 index 0、1、2、3），
所以**绝不能写死 index**。

## 七、活动页会被拼多多自己关掉

长时间运行后，活动页的 WebView 会被关掉，只剩心跳页。
这时 `resolve_target()` 抛错，需要主动把页面拉起来。

`Bridge.ensure_page()` 做**阶梯升级**：

```
第 1 次失败 → deeplink 温和打开（device.open_activity）
第 2 次起   → 冷启动（force-stop + deeplink）
```

**注意**：冷启动会杀进程 → **frida 会话失效**（`script has been destroyed`），
所以冷启动之后必须 `bridge.reconnect()`。代码里已处理。

还有个小坑：`device.open_activity()` 必须先**唤醒 + 收通知栏** ——
通知栏拉下来时前台是 `NotificationShade`，deeplink 会被投给后台实例、页面打不开。

## 八、其他零碎

| 现象 | 原因 / 处理 |
|---|---|
| `uiautomator dump` 一次要 2~30 秒 | 活动页有倒计时动画，等不到 idle。**抢兑主流程不依赖它** |
| 滚动后 `bounds` 全变 `[0,0][0,0]` | WebView 滚动后不暴露布局。所以坐标定位不可靠 |
| `dump` 失败会静默留下上次的文件 | 读到过期数据。用之前先 `rm` |
| 屏幕息屏会冻结 JS 计时器 | 开火期间必须保活（常亮 + 内核 wakelock） |
| 内核 wakelock 不持会被冻住 | `echo tag > /sys/power/wake_lock`（绑进程，进程死就释放） |
| 别的 App 会抢前台 | `guard.sh` 每 15 秒把 PDD 顶回前台 |
| 内存不足时 `dump` 被 OOM kill | `am kill-all` + `drop_caches` |
