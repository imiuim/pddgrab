# 05 · 实战复盘：2026-10-27 从 4 场全败到抢到

> 这一篇记的是**推理过程**，包括走过的弯路和怎么证伪的。
> 下次遇到「明明代码没变却抢不到」，照着这个思路排查。

---

## 一、当天战况

| 场次 | 目标 | 结果 | 错误码 |
|---|---|---|---|
| 08:00 | 可口可乐 | ❌ | 全 `250013` |
| 10:00 | 汰渍洗衣液 | ❌ | 全 `250013` |
| 20:00 | 汰渍洗衣液 | ❌ | 全 `300001`（真进窗口） |
| **22:00** | **汰渍洗衣液** | **✅ 抢到** | 300001 × 16 → **第 16 发 `ec=0`** |

## 二、走过的弯路（都被证伪了）

### 弯路 1：「按钮没翻转，得先刷新页面」→ 对，但不解决问题

**假设**：UI 路线的老结论 —— 页面挂在前台不刷新，按钮停在「待开抢」。

**做法**：加 relaunch / navigate。

**证伪**：刷新确实必要，但**刷新不能解决「请求不被认」**。
08:00/10:00 两场刷新过，错误码仍是 `250013`。

### 弯路 2：「动态定位不准」→ 定位是对的，但太慢

**假设**：商品名 `bounds=[0,0][0,0]` 导致点空。

**做法**：改成「名字行号 → 其后第一个真实坐标按钮」，加坐标缓存。

**证伪**：离线测试 28 项全过，真机 `--dry` 也过了；但真开火时
**定位耗了 96 秒**（dump 太慢），T0 之后才点下去，按钮已「已抢光」。
**坐标本身完全正确** —— 问题在「开火窗口内不该做任何读界面操作」。

### 弯路 3：「限流是因为发太快」→ 对，但结论下反了

**发现**：`250017` 在前端 bundle 里搜不到 → 做实验 → 发现间隔 <800ms 必被限流。

**当时的结论**：那就拉开到 900ms 一发。

**结果**：20:00 场 40 发全 `300001`，密度只有 1.1 发/秒，**还是没抢到**。

**再次证伪**：限流只看**并发**，不看速率。
改成「收到响应再发下一发」的串行链 → **11.6 发/秒，零限流**。
（这一步是当晚最关键的翻盘。）

### 弯路 4：「换便宜商品就能抢到」→ 换商品解决不了资格问题

**做法**：可乐（108 卡）→ 汰渍（128 卡）→ 薯片（108 卡）。

**证伪**：错误码一模一样。**资格问题跟商品无关**。
（不过换商品确实有意义 —— 库存竞争激烈程度不同。但那是第 4 层的事。）

### 弯路 5：「是不是我的代码有问题？」→ 用券做对照实验，证伪

**做法**：拿 1 张卡去兑一张券（券不限时间、随时可兑），
用的是**和兑实物一字不差的请求**。

**结果**：**券兑成功** ——
`{"success":true,"error_code":1000000,"result":{"success":true,"error_code":0}}`，
余额 132 → 131。

**结论**：接口、签名、参数、地址**全都没问题**。差异只在实物的窗口/资格。

> 这一招（`coupon` 命令）后来固化成工具，是**判断「代码有没有问题」的试金石**。

## 三、真正的两个突破

### 突破 A：`250013` vs `300001` —— 会话新鲜度

**触发**：前面几场全是 `250013`，但 10-09 那次成功时的码族是 `300001`。
**同样是「没抢到」，为什么码不同？**

**实验**：`am force-stop` 重启拼多多 + 重载活动页，然后连打 5 发。

**结果**：

| 状态 | 同样的请求 | 返回 |
|---|---|---|
| 页面存活数小时 | `{award_id, address_id, address_snapshot_id}` | **`250013`** |
| 冷启动之后 | **同一个请求** | **`300001`** |

**结论**：`250013` = 请求**没被认**；`300001` = 真的在窗口内竞争。
**开火前必须冷启动。**

**影响**：08:00/10:00 两场是「压根没参赛」，不是「参赛了没抢到」。
之前所有关于「手速/密度」的优化都是白费。

### 突破 B：限流只针对并发，串行链 11.6 发/秒

**触发**：20:00 场冷启动成功（全 300001），但 1.1 发/秒的密度不够。

**思考**：10-09 赢那次是 1 秒内 40 发。现在被限流卡在 1 发/秒。
**有没有既能高速又不触发限流的打法？**

**假设**：限流看的是「并发在途请求数」，不是「单位时间发数」。
如果**每发都等响应**，在途恒为 1，那就不该被限流。

**实验**：`x.onload = function(){ ...; fire(); }` —— 在响应回调里直接发下一发。

**结果**：

```
12 发只用 0.98 秒 → 12.2 发/秒
错误码: 全是 300001，零 250017
```

**假设成立。** 密度提升 10 倍，且零限流。

**落地**：`sniper.js` 参数改成 `gapMs=0`、`attempts=120`。

## 四、命中那一场的完整记录

**22:00 场，汰渍淡雅熏香洗衣液 1kg，128 卡**

配置：冷启动 + 串行链（gap 0）+ 首发 T-1s + 120 发上限

```
#0  drift= -1000ms  300001
#1  drift=  -996ms  300001
...
#15 drift=  +889ms  300001
#16 drift=  +975ms  ec=0        ★★★ 命中
```

返回：

```json
{"success":true,"error_code":1000000,"result":{"success":true,"error_code":0}}
```

**三重确认**：

| 证据 | 内容 |
|---|---|
| 响应 | `result.success=true, error_code=0` |
| 商品状态 | 该场 15 件商品里**只有汰渍**变 `status=11`（已兑换），其余全 `status=1`（已抢光） |
| 余额 | 131 → **3**（扣 128） |

**意外收获**：命中点是 **T+975ms** —— 说明**库存是 T+900ms 左右才释放的**，
不是 T0。所以首发必须提前到 T-1s，连续发才能兜住释放点。

---

## 五、那晚定下的三条铁律

1. **开火前必须冷启动刷新会话**（否则 `250013`，等于没参赛）
2. **只能用串行链**（并发被限流 `250017`；串行 11.6 发/秒且不限流）
3. **首发提前到 T-1s**（库存 T+900ms 才放出）

**判据口诀**：

```
看 250013 → 冷启动
看 250017 → 改串行
看 300001 → 加密度
看 0      → 成功
```

## 六、当天没解决、留给以后的问题

| 问题 | 现状 |
|---|---|
| 单账号密度上限 ≈ 11.6 发/秒 | 受 RTT ~90ms 限制。热门商品（充电宝 388 卡）库存 1~2 件时仍可能抢不到 → 需要多账号 |
| 服务端规则会变 | `250013`/`250017` 都是新码，前端 bundle 里没有。**遇到新码只能实盘试** |
| 活动页会被 App 关掉 | 已用 `ensure_page()` 阶梯升级（deeplink → 冷启动 + 重连）兜住 |
| PDD 进程偶尔自己死 | guard 会拉起；但会丢页面内的 sniper，所以 PC 侧要能重装 |
| 兑换卡数会变 | 活动页公告「10月28日0点起，由100上调至200」。**每次抢前用 `list` 现查** |
