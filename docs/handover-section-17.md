## 十七、2026-10-09 凌晨：新增拼多多「整点抢券」抢兑模块

**需求**：抢拼多多的酷态科充电宝（路径：拼多多首页搜索 `ddd` → 点活动横幅 → 进「整点抢券」），
**抢到必须自动完成兑换**。

### 17.1 先做可行性判定（不是先写脚本）

- 「免费兑商品」区用**减减卡**兑换实物，目标 `酷态科自带线充电宝 10000毫安` = **388 张**（抢前余额 405）。
- 活动规则原文：「优惠券和实物商品**库存有限，先到先得**」→ 限量**竞速**，不是抽签；
  另有「奖品兑换后**不支持撤销**」和 7.1 条「禁止使用任何插件、外挂等不正当手段参与活动」。
- 减减卡来源：**本活动页**下单、确认收货才发 40 张/单，每日上限 200 张 → 攒到 388 要很多天。
  所以**门槛在余额，不在网速**，绝大多数用户根本凑不够张数。
- 场次：0点 / 8点 / 8:30 / 9:00 … 21:00；活动页「免费兑商品」区那句「本场X点开始兑换」是权威场次说明。

### 17.2 ⚠️ 0 点场实盘失败与根因（接手必读）

**结果：没抢到**，减减卡 405 纹丝不动，页面随后变成「0点场已抢光 下一场8点开始」。

点击本身是准的：设备端脚本在 `00:00:00.087` 连点 8 次，落点误差 **83ms**，全部执行完。
两个"看起来像原因"的都不是原因：

1. **不是被别的程序抢屏**。事件日志 `wm_set_resumed_activity [... WelfareWebActivity,
   bringingFoundTaskToFront]` 显示腾讯元宝是 `00:00:19.876` 才到前台，比连点结束
   （`00:00:04.7`）晚 15 秒。（元宝引擎 `config.ini` 的 `daily_window = 00:00-02:00`
   确实会在 0-3 点随机时刻抢屏，但没赶上这一枪 —— 见第十二节。）
2. **不是没到点**，时间戳精确到毫秒。

**真正原因：活动页是 WebView，长期挂在前台不会自己重新拉数据**，按钮始终停在「待开始」，
点击打在一个 `clickable=false` 的按钮上。页面数据是在它被切到后台又切回来（Activity resume）
之后才刷新的 —— 那时已经抢光。

**结论：开抢前和开抢瞬间必须主动 refresh**，不能指望页面自己翻转。做法是
`input keyevent HOME` 后 `monkey -p com.xunmeng.pinduoduo -c android.intent.category.LAUNCHER 1`
重新拉起（实测恢复到同一个 Activity 实例、window id 不变，并重新拉数据）。

### 17.3 架构：App 编排 + root 脚本执行

**App 不自己点**。本机开了 AOSP 缓存冻结器（见第八节），App 会被冻住、无障碍服务会掉，
而抢兑窗口只有几秒，赌不起。root shell 不受冻结影响、`sleep` 精度足够、App 被杀也照样跑。

```
assets/pdd_grab_multi_slot.sh     脚本模板（占位符 __SLOTS__ 等）
      │  PddGrabDeployer.render()  用真实场次填充
      ▼
/data/local/tmp/pdd_grab.sh       经 su 写入（base64 传输，中文/引号不会被 shell 解析坏）
      │  arm()  setsid 脱离启动
      ▼
root 后台进程                      抢兑本体
```

| 文件 | 作用 |
|---|---|
| `assets/pdd_grab_multi_slot.sh` | 脚本模板，已在 `pubspec.yaml` 声明为 asset |
| `lib/services/pdd_grab_deployer.dart` | 渲染 / `su` 部署 / `setsid` 武装 / `stop` / `pid` / `readLog` / `selfTest` / `outcome` |
| `lib/services/pdd_grab_service.dart` | Dart 侧引擎（无障碍树解析、文字锚点定位按钮、自旋对时、连点、确认、对账） |
| `lib/models/pdd_grab_config.dart` | 配置/结果模型，`fromSlotLabel` 支持「明日00:00」跨天 |
| `lib/screens/pdd_grab_screen.dart` | 控制台：只读自检 / 部署并武装 / 停止，20 秒轮询日志与进程 |

每场流程：开闸前 12 秒 refresh → 开闸瞬间连点 6 次 → 找确认 → 再 refresh 再连点 12 次 → 找确认。
**成功判据是读「我的减减卡」余额下降**，不靠 UI 文案自证。

### 17.4 ⚠️ 保命约束（改脚本前必读，已有测试守着）

1. **确认词表只留 `确认兑换/确认/确定`**。页面「免费兑券」区**常驻两个可点的「立即兑换」**
   （6折券/100元券），把它当确认按钮点下去会**兑换成错券**。
2. **一旦点到确认立刻收尾**，不再 relaunch + 连点 —— 那时可能已是订单页，盲点会点到别的东西。
3. **每次连点前用 `onpage` 守住"必须在活动页"**，否则先走搜索路径重新进入。
4. **判页不能用标题**：活动标题「整点抢券」是**图片渲染**的，无障碍树里没有该 text 节点，
   判页要用 `免费兑商品` / `我的减减卡`。
5. **必须持 wakelock**：设备深睡会冻住 `sleep` 循环（特来电 `task_poll.sh` 注释也写了
   "深睡下 crond 不 tick"），脚本用 `echo pdd8 > /sys/power/wake_lock` 顶住；设备插电，代价可接受。
6. 抢兑期间**屏幕常亮**：`svc power stayon true` + `screen_off_timeout` 拉满。
7. **判页必须同时校验前台包名 + 页面独有文案**（2026-10-09 01:00 补，踩过）：
   - `uiautomator dump` 在拼多多**不在**前台时仍会吐出拼多多的树 —— 实测元宝 H5
     在前台（`topResumedActivity=...hunyuan...WelfareWebActivity`，截图确认屏幕就是元宝）
     时，dump 到的却是 `package="com.xunmeng.pinduoduo"` 的 519 个节点。
     只 grep 文案会**假阳性**，脚本会以为自己在活动页、然后在元宝页面上盲点。
   - 拼多多还有别的活动页也叫「减减卡兑好礼」，上面**同样有「我的减减卡」**，
     拿它当判据也会误判。**只有「免费兑商品」是「整点抢券」页独有文案。**
   - 所以 `onpage()` 改成：先 `case "$(fg)" in *pinduoduo*)` 确认前台包名，
     再 grep `免费兑商品`；两个都满足才算在活动页。已有单测守着这个形状。

## 十七、2026-10-09 凌晨：任务"看着没跑"的四个真因（已修三个）

**用户问**：为啥元宝任务没有运行？

**先给结论**：**跑了**。10-09 00:00 起自动窗口生效，两轮：00:00 那轮唤醒失败中止，01:10 那轮成功，积分 27500 → **50500**（含打卡第 2 天的 20000）。但页面上看着像没做——查出四个问题：

### 17.1 计数上报是错的（已修）
01:10 上报 `ask/write/photo/pimage: 0`，可福利页实际是**拍题 3/3、P图 3/3、写作 1/3**。
**根因**：读数步骤夹在流程中间，那时 App 根本不在福利页（还在生成页），无障碍树里没有那些行 → 全读成 -1 → 上报 0。
**修法**：把 5 处读数**挪到流程末尾统一读**，按页面从上到下排序（做同款 → 趣问 → 每日任务三项）；`count_task` 增加**"找不到就往下滚一屏再试，最多 4 次"**（WebView 只暴露可见节点）；正则放宽为 `\((\d)\s*/\s*3\)`，兼容趣问那种 `(x/3)` 写法。

### 17.2 通知权限被重装重置 → 全屏意图亮屏失效（已修 + 写进安装清单）
`POST_NOTIFICATION` 变成 `ignore`、AppSettings `importance=NONE` → 全屏意图通知发不出去 → 息屏时唤不醒 → 00:00 那轮 `wake_failed`。
**修法**：`pm grant ... POST_NOTIFICATIONS` **+ `appops set --uid ... POST_NOTIFICATION allow`**（只 set 包级不够，要 `--uid` 才会真正生效，实测 `granted=true`、`importance=DEFAULT`）。
**⚠️ 每次重装 APK 都会重置，装完必须补这几条**（已并入上面的安装清单）。
另：中止原因现在会区分 `wake_failed:screen_off`（没亮屏）和 `wrong_foreground:<pkg>`（前台是别的应用），便于排查。

### 17.3 轮询链重复（已修）
日志显示 poll 间隔只有 **2.5 秒**（应 60 秒）：多次重挂无障碍服务，每次 `onServiceConnected` 都新起一条 `schedulePoll` 链，旧链没人停。
**修法**：加**轮询代数** `pollGen` —— 重连时 `++pollGen` 并 `quitSafely()` 旧线程；每条链带自己的 gen，发现 `gen != pollGen || instance !== this` 就退出。实测修复后 60 秒一次。

### 17.4 福利页多了个新任务：做同款模版 ×3（1500 分，已加入引擎）
福利页新增板块「做同款模版得积分」，引擎原来完全没覆盖。
**流程**（实测）：模版卡上的「做同款」→ 打开模版页 → **右下角发送按钮 (948,2262)** → 生成即计数；做 3 次。
已加入 `buildSteps`（`tapText("做同款")` + 发送 + 生成等待 ×3），任务 key `same`，同步加进监控页与 React 组件的 `TASK_NAMES`。
