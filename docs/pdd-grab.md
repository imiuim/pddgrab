# 拼多多「整点抢券」抢兑自动化

## 活动是什么

拼多多首页搜索 `ddd` → 点顶部活动横幅 → 进入 **整点抢券**。
页面里「免费兑商品」区用**减减卡**兑换实物，例如
`酷态科自带线充电宝 10000毫安` = **388 张减减卡**。

规则原文（活动页「规则」弹窗）：

> 每天抢券场次有限，优惠券和实物商品**库存有限，先到先得**。
> 减减卡使用后不做退还。

所以这是一个**限量竞速**场次，不是抽签；胜负取决于开闸瞬间的首包时间。
场次时刻表按 `明日00:00 / 08:00 / 08:30 … 21:00` 排列，每场独立开闸。

## 为什么这个场次值得做

减减卡的获取速度是硬约束：本活动页下单确认收货才发 **40 张/单**，
每日上限 **200 张**（即每天最多 5 单）。攒到 388 张需要多日累积，
**门槛在余额而不在网速**——绝大多数用户根本凑不够张数。
因此脚本的目标不是"比人快 100ms"，而是"开闸瞬间一定在线、且不点错"。

## 代码位置

| 文件 | 作用 |
|---|---|
| `lib/services/pdd_grab_service.dart` | 抢兑引擎：无障碍树解析、坐标定位、对时、连点、确认、对账 |
| `lib/models/pdd_grab_config.dart` | 配置（目标关键字、开闸时刻、连点参数）与结果模型 |
| `test/pdd_grab_test.dart` | 单测，用**真机 dump 的原始 XML** 做夹具 |

## 设计要点

1. **只认服务端场次时刻**：开闸时间取自活动页场次表，不靠本地猜测。
2. **自旋对时**：粗睡到剩余 60ms，再用 1ms 粒度收尾。实测设备端脚本
   落点误差 **83ms**（目标 23:02:18，首次点击 23:02:18.083）。
3. **坐标动态解析**：不硬编码商品坐标。先按文字锚点找到商品名，再在
   **同列正下方 400px 内**找「立即兑换 / 待开始」按钮。布局上下浮动不会打偏，
   也保证不会串到隔壁商品（酷态科 x≈224 vs 晴雨伞 x≈571）。
4. **限速连点**：开闸后按 600ms 间隔连点 8 次，覆盖按钮翻转延迟。
   实测 `input tap` 可跑 18 次/秒，但**故意不这么做**——活动规则 7.1 明确禁止
   插件/外挂，高频轰炸既无必要（门槛在余额）又徒增风控画像。
5. **默认自动确认**：`autoConfirm` 默认 `true` —— 需求是「抢到了必须帮我兑换」。
   注意兑换会消耗减减卡并生成**不可撤销**的订单（规则 3：奖品兑换后不支持撤销），
   关掉它则只点到确认弹窗、留给人工点。
6. **对账即证据**：兑换前后读「我的减减卡」余额，差值应等于商品标价
   （388）。余额没变就是没抢到，不靠 UI 文案自证。

## 用法

```dart
final svc = PddGrabService();

// 1) 抢兑前：点亮屏幕 + 常亮 + wakelock（MIUI 会提前进 AOD，息屏后点击全部落空）
await svc.wakeScreen();
await svc.keepAwake();

// 2) 用场次标签构造配置（"明日00:00" 会自动跨天）
final cfg = PddGrabConfig.fromSlotLabel(
  '明日00:00即将开抢',
  '酷态科',
  now: DateTime.now(),
  dryRun: false,       // 干跑时保持 true
  autoConfirm: false,  // 兑换不可撤销，默认人工确认
);

// 3) 端到端：定位 → 对时 → 开闸连点 → 对账
final result = await svc.run(cfg, skipNavigation: true);
print(result.toJson());
```

`dryRun: true` 时只解析坐标并打印计划，**不发任何点击**，可安全预演。

## 已知限制

- **必须已登录**：规则 5「仅能在登录状态参与抢券」。本机 `gsm.sim.state=ABSENT`
  无 SIM 卡，手机号验证码不可达，需用微信或已存会话登录。
- **root 依赖**：走 `su -c` 调 `input` / `uiautomator`，设备需 KernelSU。
- **dump 粒度是秒级**：动态页 `uiautomator dump` 要等 idle，实测 2–12s 且偶发返回空。
  因此 dump 只用于**开闸前定位**，开闸瞬间只发点击、不做 dump。
- **规则 7.1 风险**：平台禁止插件/外挂，自动化参与有被限制活动资格的可能。
  这是账号风险，需自行权衡。

## 实盘复盘：2026-10-09 0 点场（失败，含关键教训）

第一次实盘，**没抢到**，而且失败原因反直觉，值得记下来。

现象：活动页从 23:03 起就显示「待开始」。设备端定时脚本在 `00:00:00.087` 准点连点 8 次
（落点误差 **83ms**），全部执行完毕；但减减卡 **405 纹丝不动**。等页面被顶到后台再切回来
时，已经变成「0点场已抢光 下一场8点开始」。

排查（都有一手证据）：

1. **不是被别的程序抢了屏幕**。事件日志显示腾讯元宝是在 `00:00:19.876` 才被
   `wm_set_resumed_activity [... WelfareWebActivity, bringingFoundTaskToFront]`
   顶到前台，比连点结束（`00:00:04.7`）晚了 15 秒。所以那 8 次点击确实落在拼多多上。
   （元宝引擎的 `config.ini` 写着 `daily_window = 00:00-02:00`，确实会在 0-3 点随机时刻抢屏，
   但它没赶上这一枪。）
2. **也不是没到点**。点击时间戳精确到毫秒，与目标秒误差 83ms。
3. **真正的原因是页面是"死"的**：这个活动页是 WebView，长期挂在前台**不会自己重新拉数据**，
   按钮始终停在「待开始」。点击打在一个 `clickable=false` 的按钮上，自然什么都不会发生。
   页面数据是在它被切到后台又切回来（Activity resume）之后才刷新的 —— 那时已经抢光。

**结论（已写进脚本）**：开抢前和开抢瞬间必须**主动 refresh**，不能指望页面自己翻转。
做法是 `input keyevent HOME` 后 `monkey -p com.xunmeng.pinduoduo -c android.intent.category.LAUNCHER 1`
重新拉起 —— 实测会恢复到同一个 Activity 实例（window id 不变）并重新拉数据。

## 设备端脚本：`tools/pdd_grab_multi_slot.sh`

Flutter 侧引擎负责"怎么抢对"，这个设备端脚本负责"到点一定在场"。跑在手机 root 上，
不依赖 PC 是否开机：

- **多场次**：`SLOTS` 列出 08:00/08:30/09:00/…/12:00 的开闸 epoch，逐场尝试，成功即退出。
- **每场流程**：开闸前 12 秒 refresh → 开闸瞬间连点 6 次 → 找确认 → 再 refresh 再连点 12 次 → 找确认。
- **成功判据**：读页面「我的减减卡」余额，从 405 掉到 300 以下即判定兑换成功（最硬的证据，
  不靠 UI 文案自证）。
- **保命约束**：
  - 确认词表只留 `确认兑换/确认/确定`。页面「免费兑券」区常驻两个可点的 `立即兑换`
    （6折券/100元券），误当确认按钮点下去会**兑换成错券**。
  - 一旦点到确认**立刻收尾**，不再 relaunch + 连点 —— 那时可能已是订单页，盲点会点到别的东西。
  - 每次连点前用 `onpage` 守住"必须在活动页"，否则先走搜索路径重新进入。
- **判页不能用标题**：活动标题「整点抢券」是**图片渲染**的，无障碍树里没有这个 text 节点，
  判页要用 `免费兑商品` / `我的减减卡`。
- **必须持 wakelock**：设备深睡会冻住 `sleep` 循环（特来电 bot 的注释也写了"深睡下 crond 不 tick"），
  脚本用 `echo pdd8 > /sys/power/wake_lock` 顶住；设备插电，代价可接受。
- 自带 `--test` 模式：只读页面状态和余额、不发点击，可安全预演。

## App 集成方式（推荐路径）

App **不自己点**，只做三件事：**渲染脚本 → 部署 → 武装/监控**。

```
assets/pdd_grab_multi_slot.sh        脚本模板（占位符 __SLOTS__ 等）
        │  PddGrabDeployer.render()  用真实场次填充
        ▼
/data/local/tmp/pdd_grab.sh          经 su 写入（base64 传输，避免中文/引号被 shell 解析坏）
        │  arm()  setsid 脱离启动
        ▼
root 后台进程                          抢兑本体，App 退出/被冻结都不影响
```

代码对应：

| 文件 | 职责 |
|---|---|
| `lib/services/pdd_grab_deployer.dart` | 渲染模板、`su` 部署、`setsid` 武装、`stop`/`pid`/`readLog`/`selfTest`/`outcome` |
| `lib/screens/pdd_grab_screen.dart` | 控制台：只读自检 / 部署并武装 / 停止，20 秒轮询日志与进程 |
| `assets/pdd_grab_multi_slot.sh` | 脚本模板，在 `pubspec.yaml` 里声明为 asset |

**为什么不让 App 自己点**：这台机器开了 AOSP 缓存冻结器
（`settings put global cached_apps_freezer`），App 会被冻住、无障碍服务也会掉；
而抢兑窗口只有几秒，赌不起。root shell 不受冻结影响，`sleep` 精度足够。

`PddGrabDeployer` 里所有纯函数（`render` / `parseCards` / `parseOnPage` /
`parsePid` / `halfHourlySlots`）都有单测覆盖，且其中 4 条测试专门守住上面那些
**保命约束**（确认词表不含「立即兑换」、点到确认即收尾、连点前守住活动页），
防止以后有人改脚本时把这些约束改没了。

场次由 App 现算：`halfHourlySlots(from: now, until: 结束场次)`，每 30 分钟一场，
起点**向上取整**到下一个半点（08:10 → 08:30，不能回退到已经过去的 08:00）。
