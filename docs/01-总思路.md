# 01 · 总思路

## 一、先想清楚：抢不到是哪一层的问题

一次抢兑要穿过四层，任何一层出问题都表现为「没抢到」，但**修法完全不同**：

```
  ┌─ 第 1 层：资格层 ─────────────────────────────────┐
  │  服务端认不认这个请求？                            │
  │  症状：错误码 250013（请求没被认）                  │
  │  修法：开火前 force-stop 冷启动刷新页面会话          │
  └───────────────────────────────────────────────────┘
  ┌─ 第 2 层：频率层 ─────────────────────────────────┐
  │  请求发得太密被打回？                              │
  │  症状：错误码 250017（请求过于频繁）                │
  │  修法：并发齐射 → 改串行链                          │
  └───────────────────────────────────────────────────┘
  ┌─ 第 3 层：时序层 ─────────────────────────────────┐
  │  打的时间点对不对？                                │
  │  症状：错误码 300002 / 250005（未到时间）           │
  │  修法：对时(_stm) + 首发提前到 T-1s（库存 T+900ms 才放）│
  └───────────────────────────────────────────────────┘
  ┌─ 第 4 层：密度层 ─────────────────────────────────┐
  │  进了窗口但比别人慢？                              │
  │  症状：错误码 300001（慢了一步没抢到）              │
  │  修法：串行链把密度提到 ~11.6 发/秒                 │
  └───────────────────────────────────────────────────┘
```

**前两层是「有没有资格参赛」，后两层是「参赛了能不能赢」。**
2026-10-27 那天，前面几场一直卡在第 1 层（全是 250013），
误以为是第 4 层的问题（以为要加密度）—— 加了密度也白搭，因为压根没参赛。

## 二、为什么走接口，不走模拟点击

UI 模拟点击在这个活动页上有**三个结构性死结**，跟手速无关：

| 死结 | 实测 |
|---|---|
| `uiautomator dump` 极慢 | 活动页有倒计时动画，等不到 idle，**一次 dump 要 2~30 秒** |
| 滚动后坐标全丢 | WebView 滚动之后商品名的 `bounds` 变成 `[0,0][0,0]`，定位失明 |
| 按钮不翻转 | 页面挂在前台**不会自己重新拉数据**，开闸瞬间按钮还是「待开抢」（`clickable=false`） |

而接口路线把「等页面翻转」整个删掉：**到点直接发兑换请求，页面显示什么无所谓**。

> 代价是要先搞清楚请求长什么样。好消息是：**不用逆签名**。
> 拼多多原生 App ≥4.69 的 axios 拦截器对 `useNativeAntiToken` 的请求不做 JS 签名 ——
> `anti_content` 由**原生网络层注入**。所以在页面里发一个普通 `XMLHttpRequest` 就行。
> 详见 [04-底层机制](04-底层机制.md)。

## 三、整体架构：三层防线

```
        PC 侧                                   手机侧
┌──────────────────────┐              ┌──────────────────────────┐
│ grabber（编排）       │              │ guard.sh（设备端守护）    │
│  ├ 冷启动刷新会话     │─── adb ────▶ │  ├ 到点唤醒 + 冷启动      │
│  ├ 武装 sniper        │              │  ├ 窗口内守前台           │
│  └ 盯结果 + 记日志    │              │  └ 抢完息屏               │
└──────────┬───────────┘              └──────────────────────────┘
           │ frida
           ▼
┌──────────────────────────────────────────────────────────────┐
│ sniper.js（注入到活动页 JS 上下文）                            │
│  对时 _stm → 找场次+奖品 → 找默认地址 → 自旋等到点 → 串行链连打 │
└──────────────────────────────────────────────────────────────┘
```

**为什么要三层**：

1. **sniper 在页面里** —— 只有页面里发请求才带原生签名；而且它在页面里自调度，
   PC 断开也能开火。
2. **guard 在设备上** —— PC 可能断线/休眠；设备端自己会到点冷启动、守前台。
3. **grabber 在 PC 上** —— 负责编排和记录（这是人要看的部分）。

三者解耦：`sniper` 可以单独用（`arm` 命令），`guard` 可以单独用，PC 全程不在也能跑。

## 四、一次成功抢兑的完整时序

```
T-220s   PC: grabber.run() 开始
T-215s   PC: force-stop 拼多多 → deeplink 冷启动（★ 关键：刷新会话）
T-200s   PC: frida 连接，确认「减减卡兑好礼」页可见（id=195846）
T-195s   PC: 读场次表 → 选目标（只认 start_time > now 的最近一场）
T-190s   PC: 读默认收货地址
T-185s   PC: 安装 sniper.js + 武装（fireAt = 场次开始时刻）
         —— 之后 PC 只是旁观，开火由页面自己完成 ——
T-100s   sniper: 重新对时（_stm）
T-30s    sniper: 发一发诊断探针（用来观察「未到时间」的码长什么样）
T-1s     sniper: 首发（★ 提前 1 秒 —— 实测库存在 T+900ms 才放出）
T0       sniper: 串行链开火，约 11.6 发/秒
T+975ms  ★ 命中（ec=0）
T+5s     PC: 读结果、读余额、写日志
```

## 五、设计取舍（为什么不是别的做法）

| 选择 | 为什么不选另一种 |
|---|---|
| 在页面里发 XHR | 不用逆 `libpdd_secure.so`；脱离 WebView 的请求必被判非法 |
| 串行链而不是并发齐射 | 并发被限流 250017；串行实测 11.6 发/秒且零限流 |
| 首发 T-1s 而不是 T0 | 实测库存 T+900ms 才放出，T0 才发会错过 |
| 每次开火前冷启动 | 不冷启动请求判 250013（没被认），等于没参赛 |
| 按活动 id 选页（195846） | 只按 "attendance" 会选到 197270 那个后台页，XHR 回调被冻 |
| 设备端 guard + PC 编排 | 单靠 PC，断线就全废；单靠设备，没法记录和调试 |

## 六、这套思路的边界

* **单账号 + 家宽的密度上限 ≈ 11.6 发/秒**（受 RTT ~90ms 限制）。
  热门商品（充电宝 388 卡、晴雨伞 208 卡）库存可能 1~2 件，仍可能抢不到 ——
  那是并发量问题，不是代码问题。再往上要**多账号并发**。
* 平台随时可能改服务端规则（250013/250017 就是新码，前端 bundle 里都没有）。
  **遇到新码：先 `probe` 确认链路，再用 `fire` 小规模试，看码说话。**
* 平台规则禁止插件/外挂，账号风险自负。
