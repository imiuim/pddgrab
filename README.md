## 一、30 秒上手

```bash
cd G:\vp\pdd-grab\api

# 看配置 / 设备状态
python -m pddgrab.cli env

# 列出未结束的场次和商品（含目标标记）
python -m pddgrab.cli list --item 汰渍

# 只读自检：不武装、不开火，确认链路和目标都可抢
python -m pddgrab.cli probe --item 汰渍

# 完整跑一次（冷启动 → 武装 → 盯到开火 → 出结果）
python -m pddgrab.cli fire --item 汰渍

# 指定场次时刻（默认自动取「未开始的最近一场」）
python -m pddgrab.cli fire --item 汰渍 --at 22:00
```

设备端守护（到点自动冷启动 + 守前台 + 抢完息屏，PC 可以断开）：

```bash
python -m pddgrab.cli guard --wake 21:55 --sleep 22:05
```

│   ├── cli.py                   命令行入口

## 四、★ 错误码判据（本项目的核心知识）

**同一套代码，服务端返回的码会变 —— 看清码才知道该改什么。**

| 码 | 含义 | 对策 |
|---|---|---|
| **`250013`** | **请求没被认**（页面会话旧了） | **开火前 `force-stop` 冷启动刷新页面** |
| **`250017`** | **并发快速请求被限流** | **改串行链**（等响应再发下一发） |
| **`300001`** | 在窗口内但没抢到（**真竞争**） | 提高密度（串行链 ≈11.6 发/秒） |
| `300002` / `250005` | 未到兑换时间 | 等 |
| `250003` / `250004` | 今日兑换已达上限 | 明天再来 |
| `250010` | 减减卡不够 | 做任务攒卡 |
| `0` + `result.success=true` | **成功** | — |

判断口诀：**看 250013 就冷启动，看 250017 就改串行，看 300001 就是密度不够。**

## 五、为什么必须这么做（三个关键坑，都是实盘撞出来的）

### 1. 请求必须在页面里发

拼多多原生 App ≥4.69 的 axios 拦截器对 `useNativeAntiToken` 的请求**不做 JS 签名** ——
`anti_content` 由**原生网络层**注入。所以脱离 WebView 用 curl 发会被判非法；
在页面里发一个普通 `XMLHttpRequest` 就行，不用逆 `libpdd_secure.so`。

### 2. 开火前必须冷启动刷新会话

2026-10-27 实测：页面/会话存活久了，兑换请求会被判 **`250013`（没被认）**；
`am force-stop` 重启 + 重新加载活动页之后，**同样的请求立刻变成 `300001`（真进窗口）**。
当天 08:00/10:00 两场全是 250013（白打），20:00 冷启动后全 300001。

### 3. 限流只针对「并发」，串行链不限流

| 打法 | 实测速率 | 限流 |
|---|---|---|
| 一次并发发 N 个 XHR | — | **被限流 250017** |
| 间隔 900ms 串行 | 1.1 发/秒 | 无 |
| **收到响应再发下一发（串行链，`gapMs=0`）** | **11.6 发/秒** | **零限流** |

所以 `sniper.js` 用串行链（`x.onload` 里直接发下一发），RTT ~90ms 自然形成 ~11 发/秒。
**默认参数：`attempts=120`、`gap=0`、首发 `-1000ms`。**

### 4. 顺带：库存是在 T+900ms 左右才放出来的

22:00 那场的命中点是 **drift=+975ms**（第 16 发）。所以首发要**提前到 T-1s**，
连续发才能把释放点兜住 —— 这也解释了 10-09 那次为什么是第 44 发才命中。

### 5. 目标页是 id=195846，不是 197270

拼多多同时开多个 `attendance.html`：

| id | 内容 |
|---|---|
| `197270` | 「首页搜索ddd可以找到本活动」，只有整点抢券时间条 |
| **`195846`** | **「减减卡兑好礼」，实物兑换列表在这里** |

选错页的后果：那个页在后台，`visibilityState=hidden` → **页面 XHR 回调被完全冻结**
→ sniper 装上去、`state` 看着正常，却永远卡在 `syncing`。
`webview.resolve_target()` 已按 `ACT_ID` 精确匹配，并**硬排除心跳页**
`sjs_blank_heart_beat.html`（它也会报 visible，但异步永不回调）。

## 六、命令行参考

| 命令 | 作用 |
|---|---|
| `env` | 打印当前配置 + 设备状态 |
| `list [--item X]` | 列出未结束场次与商品 |
| `probe [--item X]` | 只读自检（不武装不开火） |
| `arm [--item X] [--at HH:MM]` | 只武装（sniper 自己等到点开火） |
| `fire [--item X] [--at HH:MM] [--attempts N] [--gap MS] [--from-ms MS]` | 完整跑一次 |
| `coupon --yes` | 兑一张 1 卡券（**花 1 张卡**，用来验证链路是否通） |
| `monitor --until HH:MM [--at HH:MM] [--sniper]` | 设备状态监控（窗口内自动加密采样） |
| `guard --wake HH:MM --sleep HH:MM` | 部署设备端守护 |
| `stop-guard` | 停掉设备端守护 |

`--gap 0`（默认）就是串行链。**不要**改成小于 800ms 的并发打法。

## 八、复盘用日志

`grabber.run(log_path=...)` 和 CLI 每次运行都会写一份日志到 `logs/`，
内容包含：每一发的 `n / drift / rtt / error_code`、状态迁移、余额变化。

`monitor` 的日志是设备视角：`屏幕 / PDD 进程 / 前台`，开火窗口内 10 秒一采样，
关键节点带 `<<< 开火窗口` 标注。两相印证就能定位「那一刻到底谁在挡路」。

## 九、已知限制

* **单账号 + 家宽的密度上限 ≈ 11.6 发/秒**。热门商品（充电宝 388 卡、晴雨伞 208 卡）
  库存可能 1~2 件，仍可能抢不到 —— 那不是代码问题，是并发量问题。
* 拼多多可能随时改服务端规则（250013/250017 就是新码，前端 bundle 里都没有）。
  遇到新码：先 `probe` 确认链路，再用 `fire` 小规模试，**看码说话**。
* 平台规则禁止插件/外挂，账号风险自负。
